## 2. ★ v1에서 뒤집힌 것 — 중앙이 중앙이 아니다

v1은 좌우 50:50을 전제해 "중앙 3분할 비움"을 규칙으로 삼았습니다. 폐기합니다.

- 실제 분할선은 **가로 37.5% 지점**입니다
- **그 자리가 실물 철당간이 서는 갭**입니다
- 따라서 **소실점을 화면 정가운데(50%)에 두면 안 됩니다.** 우측 스크린 안쪽으로 밀려 엉뚱한 데 꽂힙니다

### 새 구도 규칙
1. **분할선(37.5%) 주변은 비운다** — 구조물·인물·핵심 오브젝트 금지. 실물 철당간이 그 자리를 채운다
2. **소실점은 37.5% 지점 또는 그보다 왼쪽**에 둔다. 실물 당간이 소실점을 완성하게 한다
3. **좌 37.5% 구역과 우 62.5% 구역이 각각 독립된 그림**으로 읽혀야 한다
4. 좌측은 2:1로 **가로로 길고 얕다** — 하늘·지면을 크게 못 담는다. 수평 요소 위주
5. 우측은 8:3으로 **더 넓고 더 얕다** — 파노라마에 가깝다

## 3. 기존 플레이트가 못 쓰이는 이유

21:9(2.333:1) 플레이트에서 새 창으로 잘라내면:

| | background-size | 원본 세로 사용률 |
|---|---|---|
| 좌 (37.5% 폭 → 2:1) | 266.667% | **44%** |
| 우 (62.5% 폭 → 8:3) | 160% | **55%** |

**아래 정렬이라 남는 건 바닥 띠뿐입니다.** 지붕·하늘·산이 전부 잘려나갑니다.
S5 용두사 마당으로 시뮬레이션한 결과, 좌측 스크린엔 흙바닥과 석등 밑동만 남았습니다.

즉 **해상도 문제가 아니라 구도 문제**입니다. 다시 만들어야 합니다.


## 5. 생성 경로 — 두 안

합성 4.267:1은 이미지·영상 모델의 최대 21:9(2.333:1)를 **크게 넘습니다.** 한 장으로 못 뽑습니다.

### A. 화면별 개별 생성
| | 생성 비율 | 후처리 |
|---|---|---|
| 좌 | **2:1** 직접 생성 | 없음 |
| 우 | **21:9** 생성 → 8:3으로 상하 트림 | 세로 12.5% 잘라냄 |

- 장점: 각 화면이 자기 프레임에 맞게 제대로 구성됨. 추가 도구 불필요
- 단점: **한 컷당 생성 2회**. 좌우가 별개 이미지라 지면선·광원을 프롬프트로 맞춰야 함

### B. 한 장 생성 후 가로 확장
21:9로 생성 → `images_expand`(아웃페인트)로 4.267:1까지 좌우 확장

- 장점: 좌우가 **하나의 연속된 그림**. 원래 기획 의도에 충실
- 단점: 확장 단계 추가(비용·시간), 확장부 품질이 본체보다 떨어질 수 있음

**권장: A.** 좌우 화면이 물리적으로 떨어져 있고 그 사이에 실물 당간이 서 있어서,
관객이 두 화면을 하나의 연속 이미지로 읽지 않습니다. 각 화면이 독립적으로 완결되는 편이 낫고,
생성 실패 시 한쪽만 다시 뽑으면 되므로 반복 비용도 낮습니다.

## 6. 확정값 (2026-09-10)

전체 캔버스 **5320 × 1600 = 3.325 : 1** — 절대 크기가 아니라 **비율만** 의미가 있습니다.
이 값에서 나머지가 딱 떨어집니다:

| 항목 | 값 | 도출 |
|---|---|---|
| **갭** | **200** | 5320 − 1920 − 3200 |
| **좌측 세로 오프셋** | **640** | 1600 − 960 (좌측 하단 = 캔버스 하단) |
| 좌측 위치 | x 0, y 640 | |
| 우측 위치 | x 2120, y 0 | |
| 분할선 중심 | 전체 폭의 **37.97%** | 실물 철당간 자리 |
| 좌측이 더 내려간 양 | **400px** | 좌 하단 1600 vs 우 하단 1200 |

### 렌더러 상수 (`build_web.py` 상단)
```python
GAP      = 200
OFFSET_L = 640
SCR = {"L": dict(w=1920, h=960,  x=0,        y=OFFSET_L),
       "R": dict(w=3200, h=1200, x=1920+GAP, y=0)}
```
수치가 바뀌면 이 두 상수만 고치면 크롭·CSS·프리뷰가 전부 따라갑니다.

## 7. 렌더러 동작 (구현 완료)

1. **실제 크롭 파일 생성** — 플레이트를 캔버스 폭에 맞춰 **아래 정렬**로 얹고,
   좌/우 스크린 영역을 잘라 `<이름>__L.jpg` · `<이름>__R.jpg` 로 저장합니다. CSS 눈속임이 아닙니다.
2. **실제 위치로 배치** — 두 화면을 캔버스 좌표 그대로 절대 배치. 우측이 위, 좌측이 640 아래.
   그 사이 갭에 실물 철당간 위치를 금색 선으로 표시합니다.
3. **원본 플레이트에 사용 영역 오버레이** — 빨강=좌측, 파랑=우측이 실제로 쓰는 부분.
4. **클릭하면 내려받기** — 플레이트를 클릭하면 원본, 각 화면을 클릭하면 그 화면 크롭이 받아집니다.

## 8. 구성 규칙 v5 — 컷당 3버전 체제로 확정 (2026-09-10)

### 세로는 반드시 29% 버려진다
모든 모델의 생성 상한이 **21:9(2.357:1)** 다. gpt-2의 3:1은 카탈로그에만 있고 실제로는 거부되며,
`images_expand` 아웃페인트도 21:9가 상한이다. **3.325:1을 직접 뽑을 방법은 없다.**
캔버스 폭에 맞추면 플레이트 높이가 2257px가 되고 캔버스는 1600px이므로 **657px(29%)가 버려진다.**

### ★ 아래 정렬을 폐기하고 위/아래로 나눈다 — `ALIGN_Y = 0.62`
아래 정렬(위 29%를 통째로 버림)은 좌측 스크린이 원본 **아래 42%만** 보게 만들어
전각 지붕이 전부 잘려나갔다. 버리는 양을 **위 62% / 아래 38%**로 나눈다.

| | 플레이트에서 보이는 세로 구간 |
|---|---|
| 좌측 스크린 | **46.4% ~ 88.9%** |
| 우측 파사드 | **18.0% ~ 71.2%** |
| 두 화면이 공유 | 46.4% ~ 71.2% (24.8%뿐) |

플레이트 바닥을 조금 버리는 건 싸다 — 대개 빈 마당·물이고, 광장 바닥은 어차피 별도 투사면이다.
`build_web.py` 상단 `ALIGN_Y` 하나만 고치면 크롭·프리뷰·오버레이가 전부 따라간다.

### 프롬프트 규칙 — 존 지시가 아니라 카메라 지시로
"상단 1/3은 버려진다" 같은 지시는 **쓰지 않는다.** 영상화용 소스라
프레임 안에서 잘린 그림이 나오면 못 쓴다. 대신 카메라로 말한다:

1. **가까운 것을 두지 않는다** — "no foreground object, no near building, nothing close to the lens".
   모델은 "large main hall on the left"라고 쓰면 반드시 화면을 채우는 히어로 건물을 그린다.
2. **높이를 %로 못 박는다** — "every roof ridge at 58% or lower, every base at about 72%,
   measured from the top of the frame". 존이 아니라 **지면선과 능선의 높이**로 지시한다.
3. **비유를 준다** — "a village seen from across a wide river", "a monastery seen from the
   opposite mountain". 수치만으로는 잘 안 먹고 비유가 들어가면 확률이 크게 오른다.
4. **온전함을 명시한다** — "every building is complete, with clear air above and below,
   none touching any frame edge".
5. **가로 연속** — "runs continuously across the full width, no empty vertical band, no seam".

### 검증 절차 (매 컷 필수)
플레이트를 5320×1600 캔버스에 `ALIGN_Y`로 얹고 좌(빨강)·우(파랑) 사각형을 그려
**주 피사체가 사각형 안에 여백까지 두고 들어오는지** 눈으로 확인한다. 딱 맞으면 실패다.

### ★ 세트 일관성은 텍스트로 못 잡는다 — 이미지 레퍼런스로 묶는다
S5~S8c는 고정 카메라에 날씨만 바뀌는 시퀀스인데, 같은 문장으로 따로 생성하니
**매번 다른 절**이 나왔다. 4회를 반복해도 안 됐다.
확정본 S5를 `references:[{type:"image"}]`로 물려서 "카메라·건물 배치·크기는 그대로,
날씨와 빛만 바꿔라"로 지시하니 한 번에 해결됐다. 세트가 있는 컷은 무조건 이 방식을 쓴다.

### 프롬프트에 퍼센트 수치를 쓸 때의 함정
"roof ridge at 58%" 같은 지시는 잘 먹히지만, 한 번은 모델이 그 **수치를 화면에 점선과
라벨로 그려 넣었다**(S15 후보 1장 폐기). 수치 지시를 쓸 때는 `no text, no lettering,
no numbers`를 반드시 함께 넣는다.

### 인물은 "전신"이 아니라 "서 있지 마라"로 지시한다
"full length, head to feet"만으로는 서 있는 인물의 머리가 계속 좌측 스크린 위로 나갔다.
좌측 스크린이 원본 세로의 46~89%만 보기 때문이다.
S4b는 **"NOBODY IS STANDING — 전원 쪼그려·앉아·무릎"**으로 바꾸자 한 번에 해결됐다.

### ★ 우측 파사드에는 꺾이는 선이 있다 (2026-09-11 클라이언트 확인)
우측 파사드는 평면이 아니라 **모서리로 꺾인 두 면**이다. 꺾임선 위치:

| | 값 |
|---|---|
| 파사드 폭 기준 | **58%** |
| 캔버스 x | **3976** |
| 전체 폭 기준 | **74.7%** |

**주 피사체를 이 선에 걸치지 않는다.** 갭(36.1~39.8%)과 함께 **두 개의 금지선**이 생긴 셈이다.
배경·지면·하늘·물·군중은 자유롭게 통과시켜도 되고, 작거나 스쳐 지나가는 인물도 괜찮다.
`build_web.py` 의 `FOLD_R = 0.58` 로 관리하며 보드에 노란 점선으로 표시된다.

### ★ 프롬프트에 "seam / line / 38%" 같은 말을 쓰면 모델이 그려버린다
금지선을 지키게 하려고 "physical seams at 38% and 75%"라고 썼더니
**모델이 그 자리에 실제 세로 선을 그려 넣었다**(S0 후보 1장 폐기).
앞서 퍼센트 수치가 라벨로 찍힌 것과 같은 현상이다. 금지선은 선으로 말하지 말고
**"피사체는 화면 폭 44~70% 사이에 둔다"처럼 배치 범위로만** 지시하고,
`no lines, no borders, no panel divisions, no numbers` 를 부정문에 넣는다.


### ★ S0 배는 목선이 아니라 현대 강선이다 (2026-09-11 클라이언트 확인)
피드백 원문: **"배의 선미가 더 거대하게 보이게 나룻배가 아닌 현대의 큰 배여야 함"**.
참조로 받은 3D 배가 목선이라 처음엔 크기만 키우고 선체를 그대로 뒀는데, **오독이었다.**

확정 사양:
- 선체 = **현대 대형 강선의 선수**. 수직에 가까운 스템, 바깥으로 벌어진 플레어 외판,
  파이프 난간을 두른 포캐슬 갑판, 호즈파이프와 스톡리스 앵커, 외판의 용접 스트레이크 라인,
  안개에 잠긴 구상선수. 목선·나룻배·정크·범선 전부 금지
- 그 강철 갑판 위에 **용두 철당간이 돛대로** 서고 사각 범포가 걸린다 — 이 시대 충돌이 작품의 핵
- 거대함은 **형태와 디테일**로 만들고 화면을 꽉 채워서 만들지 않는다.
  배는 화면 세로의 가운데 절반만 차지하고 위아래로 안개 여백을 크게 둔다
  (우측 파사드가 원본 세로의 18~71%만 보기 때문)

### ★ 클라이언트 레이아웃 도면 반영 (2026-09-11)
매싱 모델 스크린샷으로 **실제 배치 의도**를 받았다. 내 추정과 반대였다.

**S0 배**
- 좌측 스크린: **완전히 비움** — 위는 어두운 보이드, 아래는 옅은 안개 띠, 그 사이 부드러운 수평선뿐
- 우측 파사드: **배가 꽉 채운다.** 선수를 정면으로 들이밀고 갑판·선교·마스트가
  오른쪽으로 물러나며 계단처럼 이어진다. 흘수선에 붉은 띠
- 즉 "작게 물려서 배치"가 아니라 **가까이·크게**가 맞다

**S5 용두사**
- 좌측 스크린: **전각 한 채**만, 좌우에 큰 소나무가 서서 액자처럼 감싼다. 온전히
- 우측 파사드: 긴 낮은 전각 → 더 높은 맞배 전각 → (꺾임선 너머) 소나무 두 그루와
  또 다른 전각, 발치에 낮은 둔덕
- 모두 **하나의 낮은 지면선**에 정면 입면으로 늘어선다. 우측 건물들이 좌측 전각보다
  화면에서 더 높이 앉는다(파사드가 640px 위에 있으므로)

이 배치를 S6·S7·S8a·S8c에 이미지 레퍼런스로 물려 날씨만 바꿨다.

### ★ 결정판 — 카메라를 뒤로 빼는 것이 유일한 해법 (2026-09-11)
"존을 지정한다"로 우회해 온 게 계속 실패했다. 물리는 단순하다:

| | 원본 세로에서 보이는 구간 |
|---|---|
| 무조건 버려짐 | 위 **18%**, 아래 **11%** |
| 좌측 스크린 | 46 ~ 89% |
| 우측 파사드 | 18 ~ 71% |

그래서 프롬프트 첫 문단을 이렇게 고정한다:
> 투사 시 **위 5분의 1과 아래 10분의 1은 버려진다**. 거기엔 빈 하늘·안개·물·맨바닥만 둔다.

## 11. ★ 레이아웃 블랙바 — 버려지는 영역을 바로 굽는다 (2026-09-13)

`ALIGN_Y = 0.62` 에서 역산하면 21:9 플레이트의 **위 18.49% / 아래 11.33%** 는
캔버스에 얹는 순간 무조건 버려진다. 남는 띠는 70.18%, 비율로는 정확히 **3.325:1**
— 캔버스 5320×1600 과 같다.

그래서 r8 라운드부터 **생성 직후 그 두 영역을 순수 검정으로 덮어** 플레이트에 굽는다.
보드에 보이는 그림이 곧 투사되는 그림이 된다.

```python
TOP, BOT = 0.1849, 0.1133
d.rectangle([0, 0, w, int(h*TOP)], fill=(0,0,0))
d.rectangle([0, h-int(h*BOT), w, h], fill=(0,0,0))
```

바 없는 원본은 `images/_full/` 에 남긴다 — 영상 생성에는 그쪽을 쓴다.
검증은 캔버스에 얹은 뒤 상·하단 8행의 평균 휘도가 0이 아닌지 보면 된다.

## 15. ★ ALIGN_Y 일괄 적용 폐기 — 컷마다 세로 위치를 잡는다 (2026-09-13)

`ALIGN_Y = 0.62` 을 전 컷에 똑같이 먹였더니 S5 용두사에서 **우측 파사드에 바닥이
한 줄도 안 보였다.** 우측 파사드는 캔버스의 **위쪽 띠**(y 0–1200)를 보기 때문에,
눈높이 구도에서 지면선을 우측 안으로 넣으려면 바닥 정렬에 가깝게 가야 한다.

| S5 r10 vb (ar 2.333, ph 2280) | 지면선이 앉는 캔버스 y | 우측 파사드 안? |
|---|---|---|
| align 0.62 | 1190 | 경계선에 걸려 바닥이 안 보임 |
| align 0.993 | 932 | 아래로 268px 의 마당이 남음 |

**그래서 세 가지를 바꿨다.**

1. **블랙바를 굽지 않는다.** align 이 컷마다 다르면 바 위치도 달라져야 하므로
   플레이트에서 바를 걷어내고(`_full/` 에서 복원) 버려지는 영역은 align 에서 파생시킨다.
2. **보드의 두 화면을 라이브 창으로 바꿨다.** 미리 구운 크롭 JPEG 대신 플레이트 위에
   `<img>` 를 얹고 `width/left/top` 을 % 로 계산한다. 슬라이더를 끌면 즉시 움직인다.
3. **align 은 이미지 단위로 저장한다.** `localStorage['dotdae_sb_align_v1']`,
   키는 이미지 경로. 버전을 바꾸면 그 이미지에 저장된 값이 따라온다.

### 자동 제안값
행별 가로 엣지 에너지의 최대 지점을 지면선으로 보고, 그 선이 **우측 파사드 높이의
78%** 에 오도록 align 을 역산한다. 피크가 중앙값의 2.2배에 못 미치면(구름·물속·암전)
제안하지 않는다. 183개 버전에 기록해 뒀다.

**자동값을 그대로 믿으면 안 된다.** 눈높이 구도에서는 대부분 1.0 근처로 saturate 하고,
그러면 좌측 스크린에서 전각 지붕이 날아간다. 좌우는 한 장에서 잘라내는 것이라 맞바꿈이
있고, 어디를 살릴지는 컷마다 사람이 정해야 한다. 자동은 출발점일 뿐이다.

### 확정
`export_pdf.py --write-align` 으로 `shots.json` 의 `variants[].align` 에 굽는다.
그 뒤 `build_web.py` 를 다시 돌리면 보드 기본값이 된다.

## 16. ★ 룩 방향 — 기반은 사실적으로, 색은 효과에 (2026-09-13 클라이언트)

세 번의 지적을 거쳐 정리된 규칙이다.

1. **"시네마틱 실사 아니야, 색감들이 다 살아있어야해"** — 그동안 쓰던
   `photoreal cinematic matte painting` + `muted / desaturated` 는 틀렸다.
   야간 파사드 투사에서 채도 낮은 화면은 그냥 죽는다.
2. **"지금은 너무 갔어, 이질적이면 안돼"** — 그래서 건물·산까지 네온으로 물들여
   봤더니(테스트 r13) 완전히 이질적이었다. 폐기했다.
3. **"파도 효과나 파티클 등에서 색감을 줘야지. 비현실적이면 안돼"** ← **이것이 규칙이다.**

| | 어떻게 |
|---|---|
| **기반** (건물·산·지면·하늘) | 사실적으로 유지. 재질과 광원이 납득돼야 한다 |
| **효과** (물·파도·불·쇳물·파티클·빛줄기) | **여기에 색을 싣는다.** 채도와 발광을 올려도 된다 |
| 금지 | 기반의 전면 스타일화, 네온 색조, 비현실적 팔레트 |

### 확인된 사례 — S8b 파도
- `갈색 r11` : 흙탕물. 사실적이지만 색이 죽어 칙칙하다. ✗
- **`청색3D r12` : 건물과 산은 그대로 사실적이고 파도만 푸른 3D 유체로 색이 산다. ○**

프롬프트로 옮기면, 기반은 그대로 두고 효과 요소에만 이런 문장을 붙인다.

```
translucent, light refracting through the body of the water, crisp specular
highlights ... while the temple buildings behind stay grounded and real.
```

**아직 반영 안 된 것** — r8~r11 의 나머지 컷들은 여전히 예전 룩(muted photoreal)으로

## 18. ★ 좌우 반전 · 유물 밀도 · 엔딩 분할 (2026-09-13)

### 좌우 반전 기능
보드 「세로 위치」 줄에 **⇄ 좌우 반전** 버튼을 붙였다. 이미지만 뒤집고

구현은 두 군데다. 플레이트는 배경을 `.pbg` 안쪽 span 으로 빼고 거기에만
`scaleX(-1)` 을 건다(테두리 표시는 안 뒤집힌다). 스크린 창은 img 에 `scaleX(-1)` 만

> **★ 미러를 두 번 걸면 안 된다 (2026-09-13 수정)**
> 처음에 `left` 를 `-(CW - r.x - r.w)` 로 미러 좌표까지 바꿨다가 크롭이 엉뚱한
> 영역을 봤다. img 가 캔버스 폭 전체를 덮으므로 `scaleX(-1)` 하나로 이미 캔버스
> 전체가 뒤집힌다. 창은 제자리(`left = -r.x`)에서 그대로 잘라내면 된다.
> 원칙은 **원본만 뒤집고 크롭은 크롭만 한다** — 파이썬 쪽(`ImageOps.mirror` 후
> 같은 박스로 crop)과 결과가 일치해야 하고, 실제로 대조해서 확인했다.

| 어디 | 저장 |

### 세 라운드가 걸린 이유 — 두 가지 함정

**① "Match @Image1 exactly" 만으로는 부족하다.** 레퍼런스는 색을 잡아 주지만
모델이 **수평선을 그려 넣는다.** S1b 는 하늘과 산 능선이 있는 풍경이 나왔고,
S9 는 위가 밝고 아래가 어두운 측면 수중샷이 나왔다. 바닥 투사면은 그러면 안 된다.

> `The ENTIRE frame, edge to edge, is … seen from directly overhead.`
> `NO horizon. NO sky. no near-far perspective gradient; the camera looks straight
> down at the nadir so it fills the frame evenly.`

**② 레퍼런스는 방향을 정하지 못한다.** 같은 프롬프트가 S4b 는 18%p 어둡게,
S9 는 13%p 밝게 냈다. 레퍼런스를 물리는 것과 별개로 **어느 쪽으로 틀렸는지를
말로 덧붙여야** 한다 — "make it BRIGHT like a sunlit field at midday, do not render
it as dark grass in shadow" / "keep it VERY DARK, if in doubt make it darker still".

**③ 지면부와 비교하라.** S4b 는 플레이트 전체로는 잔디 바닥이 맞아 보였지만
지면부 RGB (144,130,109) 대비 바닥이 (101,110,45) 였다 — 플레이트 바닥은 따뜻한
흙길인데 바닥판만 초록 잔디였다. 색차를 지면부 기준으로 재고 나서야 드러났다.

## 21. 보드 버그 — 버전 바꿔도 옛 이미지가 내려받아짐

플레이트 배경을 안쪽 `<span class="pbg">` 로 옮기면서 (좌우 반전이 오버레이까지
뒤집던 문제를 고치느라) `setBg()` 가 `href` 를 갱신하지 못하게 됐다.
`setBg` 는 `el.tagName==='A'` 일 때만 `href` 를 고치는데, 이제 배경을 받는 건
`<span>` 이라 바깥 `<a class="plate" download>` 는 **처음 렌더된 1번 안**을 계속
가리켰다. 버전을 바꿔도 클릭하면 옛 이미지가 내려받아진다.

```js
setBg(plate?plate.querySelector('.pbg'):null, b.dataset.p);
if(plate && b.dataset.p) plate.href=b.dataset.p;   /* ← 추가 */
```

바닥 `.fl` 과 좌우 분할 `.sL/.sR` 은 여전히 `<a>` 가 직접 배경을 들고 있어
영향이 없다.

## 22. 내려받기 — 파일명과 원본

### 파일명은 전부 ASCII

맥은 한글 파일명을 NFD 로 풀어 저장해서 깨진다. 디스크의 원본 이름은 한글
그대로 두고(`shots.json` 이 그 이름에 물려 있다), `<a download="…">` 에 **값**을
넣어 내려받을 때의 이름만 갈아끼운다.

```
C11_SQ1_S05_plate_v1.jpg      컷번호 · 씬번호 · 컷ID · 종류 · 버전
C11_SQ1_S05_floor_1.jpg
C21_SQ4_S14_screenL_v1.jpg    좌우 분할 컷
```

앞의 `C01`–`C27` 이 이야기 순서라 한 폴더에 모으면 저절로 정렬된다. 컷 ID 는
두 자리로 맞춘다(`pad_sid`: S5 → S05, S1b → S01b). 버전 버튼마다 `data-dl` 을
실어 두고, 버전을 바꾸면 `href` 와 함께 이 이름도 갱신한다.

> **한계** — 그냥 클릭하면 이 이름으로 저장되지만, **우클릭 → 링크를 다른 이름으로
> 저장**은 브라우저에 따라 원본 한글 이름으로 떨어질 수 있다. 클릭으로 받을 것.

인쇄 PDF 의 기본 파일명은 `document.title` 에서 오므로, 인쇄하는 동안만
`Jeogyeong_storyboard_<날짜>` 로 바꾸고 되돌린다. 선택 JSON 은
`jeogyeong_storyboard_picks.json`.

### 보는 것과 받는 것을 분리한다

`shrink()` 는 긴 변을 **1600px · JPEG q88** 로 줄인다. 27컷을 한 페이지에 띄우려면
그래야 한다. 그런데 클릭해서 내려받는 것까지 그 사본이면 안 된다.

| | 폴더 | 크기 | 쓰임 |
|---|---|---|---|
| 표시 | `images/` | 1600px q88 · 124 MB | 배경·크롭·버전 썸네일 |
| 내려받기 | **`orig/`** | **손대지 않은 원본 · 356장 263 MB** | `href` 가 가리키는 곳 |

`copy_orig()` 가 원본을 바이트 그대로 `orig/` 에 복사하고 해상도를 읽어 둔다.
`href` 는 `orig/`, 배경(`.pbg`)과 스테이지 `<img>` 는 계속 `images/` 다. 버전을
바꾸면 `data-o` 로 `href` 를, `data-res` 로 플레이트 우측 해상도 뱃지를 갱신한다.

원본은 생성 당시 해상도 그대로다 — 21:9 플레이트는 3024×1296, 바닥은 2048×2048.
다만 **S5 포토샵 수정본만 1600×685** 로, 이것만은 원본 자체가 작다.
