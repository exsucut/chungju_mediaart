# 화면 사양 v2 — 최종 스크린 확정

2026-09-10 · v1(좌 16:9 / 우 4:3)을 폐기하고 실측 사양으로 교체

---

## 1. 확정 사양

| | 좌측 스크린 | 우측 파사드 |
|---|---|---|
| 해상도 | **1920 × 960** | **3200 × 1200** |
| 비율 | **2.000 : 1** | **2.667 : 1** (8:3) |
| 합성 폭 비중 | **37.5%** | **62.5%** |

합성 캔버스(갭 0 기준) **5120 × 1200 = 4.267 : 1**

두 화면 **높이가 다릅니다**(960 vs 1200). 지면선을 잇기 위해 **아래 정렬**을 기본으로 합니다.

---

## 2. ★ v1에서 뒤집힌 것 — 중앙이 중앙이 아니다

v1은 좌우 50:50을 전제해 "중앙 3분할 비움"을 규칙으로 삼았습니다. 폐기합니다.

- 실제 분할선은 **가로 37.5% 지점**입니다
- **그 자리가 실물 철당간이 서는 갭**입니다
- 따라서 **소실점을 화면 정가운데(50%)에 두면 안 됩니다.** 우측 스크린 안쪽으로 밀려 엉뚱한 데 꽂힙니다

### 새 구도 규칙
1. **분할선(37.5%) 주변은 비운다** — 구조물·인물·핵심 오브젝트 금지. 실물 철당간이 그 자리를 채운다
2. **소실점은 37.5% 지점 또는 그보다 왼쪽**에 둔다. 실물 당간이 소실점을 완성하게 한다
3. **좌 37.5% 구역과 우 62.5% 구역이 각각 독립된 그림**으로 읽혀야 한다
4. 좌측은 2:1로 **가로로 길고 얕다** — 하늘·지면을 크게 못 담는다. 수평 요소 위주
5. 우측은 8:3으로 **더 넓고 더 얕다** — 파노라마에 가깝다

## 3. 기존 플레이트가 못 쓰이는 이유

21:9(2.333:1) 플레이트에서 새 창으로 잘라내면:

| | background-size | 원본 세로 사용률 |
|---|---|---|
| 좌 (37.5% 폭 → 2:1) | 266.667% | **44%** |
| 우 (62.5% 폭 → 8:3) | 160% | **55%** |

**아래 정렬이라 남는 건 바닥 띠뿐입니다.** 지붕·하늘·산이 전부 잘려나갑니다.
S5 용두사 마당으로 시뮬레이션한 결과, 좌측 스크린엔 흙바닥과 석등 밑동만 남았습니다.

즉 **해상도 문제가 아니라 구도 문제**입니다. 다시 만들어야 합니다.

## 4. 렌더러 반영 (완료)

`build_web.py` · `build_board.py`

```css
.cL,.fL{aspect-ratio:2/1}    /* 좌 1920×960 */
.cR,.fR{aspect-ratio:8/3}    /* 우 3200×1200 */
.cL{background-size:266.667% auto; background-position:left bottom}
.cR{background-size:160% auto;     background-position:right bottom}
```

보드의 좌·우 프리뷰가 이제 실제 스크린과 같은 비율로 잘립니다.

## 5. 생성 경로 — 두 안

합성 4.267:1은 이미지·영상 모델의 최대 21:9(2.333:1)를 **크게 넘습니다.** 한 장으로 못 뽑습니다.

### A. 화면별 개별 생성
| | 생성 비율 | 후처리 |
|---|---|---|
| 좌 | **2:1** 직접 생성 | 없음 |
| 우 | **21:9** 생성 → 8:3으로 상하 트림 | 세로 12.5% 잘라냄 |

- 장점: 각 화면이 자기 프레임에 맞게 제대로 구성됨. 추가 도구 불필요
- 단점: **한 컷당 생성 2회**. 좌우가 별개 이미지라 지면선·광원을 프롬프트로 맞춰야 함

### B. 한 장 생성 후 가로 확장
21:9로 생성 → `images_expand`(아웃페인트)로 4.267:1까지 좌우 확장

- 장점: 좌우가 **하나의 연속된 그림**. 원래 기획 의도에 충실
- 단점: 확장 단계 추가(비용·시간), 확장부 품질이 본체보다 떨어질 수 있음

**권장: A.** 좌우 화면이 물리적으로 떨어져 있고 그 사이에 실물 당간이 서 있어서,
관객이 두 화면을 하나의 연속 이미지로 읽지 않습니다. 각 화면이 독립적으로 완결되는 편이 낫고,
생성 실패 시 한쪽만 다시 뽑으면 되므로 반복 비용도 낮습니다.

## 6. 확정값 (2026-09-10)

전체 캔버스 **5320 × 1600 = 3.325 : 1** — 절대 크기가 아니라 **비율만** 의미가 있습니다.
이 값에서 나머지가 딱 떨어집니다:

| 항목 | 값 | 도출 |
|---|---|---|
| **갭** | **200** | 5320 − 1920 − 3200 |
| **좌측 세로 오프셋** | **640** | 1600 − 960 (좌측 하단 = 캔버스 하단) |
| 좌측 위치 | x 0, y 640 | |
| 우측 위치 | x 2120, y 0 | |
| 분할선 중심 | 전체 폭의 **37.97%** | 실물 철당간 자리 |
| 좌측이 더 내려간 양 | **400px** | 좌 하단 1600 vs 우 하단 1200 |

### 렌더러 상수 (`build_web.py` 상단)
```python
GAP      = 200
OFFSET_L = 640
SCR = {"L": dict(w=1920, h=960,  x=0,        y=OFFSET_L),
       "R": dict(w=3200, h=1200, x=1920+GAP, y=0)}
```
수치가 바뀌면 이 두 상수만 고치면 크롭·CSS·프리뷰가 전부 따라갑니다.

## 7. 렌더러 동작 (구현 완료)

1. **실제 크롭 파일 생성** — 플레이트를 캔버스 폭에 맞춰 **아래 정렬**로 얹고,
   좌/우 스크린 영역을 잘라 `<이름>__L.jpg` · `<이름>__R.jpg` 로 저장합니다. CSS 눈속임이 아닙니다.
2. **실제 위치로 배치** — 두 화면을 캔버스 좌표 그대로 절대 배치. 우측이 위, 좌측이 640 아래.
   그 사이 갭에 실물 철당간 위치를 금색 선으로 표시합니다.
3. **원본 플레이트에 사용 영역 오버레이** — 빨강=좌측, 파랑=우측이 실제로 쓰는 부분.
4. **클릭하면 내려받기** — 플레이트를 클릭하면 원본, 각 화면을 클릭하면 그 화면 크롭이 받아집니다.
